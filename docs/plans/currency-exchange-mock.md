# Implementation Plan — Currency Exchange (Mock)

**Ticket:** Currency exchange (Mock)
**Branch:** `ai/currency_plan_1`
**Status:** Plan (for review)

## 1. Goal & Scope

Add a **mocked** `POST` endpoint that performs a currency exchange (conversion)
calculation. The purpose of this ticket is to **design and ship the API
contract** (request/response schema, validation, error handling, layering) and
return deterministic mocked results — **no real FX-rate provider integration**
is performed. Real integration options are proposed in section 7 so a follow-up
ticket can wire in a live rate source without changing the public contract.

### In scope
- New `POST /api/currency/exchange` endpoint.
- Pydantic request/response schemas with validation.
- A `CurrencyExchangeService` returning deterministic mock rates.
- Dependency-injection wiring consistent with the existing codebase.
- Unit tests for the endpoint and service.
- OpenAPI docs (auto-generated by FastAPI) reflecting the contract.

### Out of scope
- Calling any external FX API / live rates.
- Persisting exchange history to the database.
- Auth / rate limiting (noted as future considerations).

## 3. Proposed API Contract

### Endpoint
`POST /api/currency/exchange`

Chosen because the operation takes a structured input body (amount + currency
pair) and is a computation/command — a POST body is the correct fit (vs. a GET
with query params). It also leaves room to later add idempotency keys / audit
side-effects without changing the verb.

### Request body — `CurrencyExchangeRequest`
| Field           | Type            | Rules                                             |
|-----------------|-----------------|---------------------------------------------------|
| `from_currency` | `str`           | ISO 4217, 3 uppercase letters (e.g. `USD`)        |
| `to_currency`   | `str`           | ISO 4217, 3 uppercase letters (e.g. `EUR`)        |
| `amount`        | `Decimal`       | `> 0`, finite; use `Decimal` for money precision  |

```json
{
  "from_currency": "USD",
  "to_currency": "EUR",
  "amount": "100.00"
}
```

Validation notes:
- Normalize currency codes to uppercase; validate with a regex/`constr`
  (`^[A-Z]{3}$`) and against a small supported-currency set for the mock.
- Use `Decimal` (not `float`) for `amount` and monetary outputs to avoid
  floating-point rounding artifacts; configure Pydantic to serialize as string
  or number consistently.

### Response body — `CurrencyExchangeResponse`
| Field              | Type        | Notes                                        |
|--------------------|-------------|----------------------------------------------|
| `from_currency`    | `str`       | Echoes normalized input                      |
| `to_currency`      | `str`       | Echoes normalized input                      |
| `amount`           | `Decimal`   | Original amount                              |
| `rate`             | `Decimal`   | Mock rate applied (`to` per 1 `from`)        |
| `converted_amount` | `Decimal`   | `amount * rate`, rounded to 2 dp (bankers)   |
| `provider`         | `str`       | `"mock"` (future: `"ecb"`, `"fixer"`, …)     |
| `as_of`            | `datetime`  | UTC timestamp the rate is "valid as of"      |

```json
{
  "from_currency": "USD",
  "to_currency": "EUR",
  "amount": "100.00",
  "rate": "0.9250",
  "converted_amount": "92.50",
  "provider": "mock",
  "as_of": "2026-07-01T00:00:00Z"
}
```

### Status codes & errors
- `200 OK` — successful conversion.
- `422 Unprocessable Entity` — schema/validation failure (FastAPI default for
  Pydantic errors; e.g. malformed body, non-positive amount).
- `400 Bad Request` — semantically invalid but well-formed (e.g. unsupported
  currency code in the mock's supported set). Returned via `HTTPException` with
  a structured detail payload.
- Same-currency (`from == to`) resolves to `rate = 1` and `converted_amount ==
  amount` (documented behavior, not an error).

## 4. Mock Rate Strategy

`CurrencyExchangeService` computes rates deterministically so tests are stable:

- Maintain a small static table of rates relative to a base (e.g. USD):
  `{"USD": 1.0, "EUR": 0.925, "GBP": 0.79, "JPY": 157.0, "PLN": 3.95}`.
- Cross rate: `rate(from→to) = table[to] / table[from]`.
- `as_of` = a fixed/injected UTC timestamp (injectable for testability rather
  than calling `datetime.utcnow()` directly inside the service).
- Unsupported currency → raise a domain error mapped to `400`.

This keeps the mock deterministic and makes the swap to a live provider a matter
of replacing the rate lookup, not the math or contract.

### Sketch — router
```python
# zws/routes/currency.py
from fastapi import APIRouter, Depends
from zws.dependencies import get_currency_exchange_service
from zws.schemas.currency_exchange_schema import (
    CurrencyExchangeRequest, CurrencyExchangeResponse,
)
from zws.services.currency_exchange_service import CurrencyExchangeService

currency_router = APIRouter()

@currency_router.post("/exchange", response_model=CurrencyExchangeResponse)
def exchange_currency(
    payload: CurrencyExchangeRequest,
    service: CurrencyExchangeService = Depends(get_currency_exchange_service),
) -> CurrencyExchangeResponse:
    return service.convert(payload)
```

### Sketch — dependency provider
```python
# zws/dependencies.py (addition)
def get_currency_exchange_service() -> CurrencyExchangeService:
    return CurrencyExchangeService()
```

## 6. Testing Plan

Use FastAPI `TestClient` (Starlette) + `pytest`:
1. **Happy path** — `USD→EUR`, amount `100` → `200`, correct `rate`,
   `converted_amount`, echoed fields, `provider == "mock"`.
2. **Same currency** — `USD→USD` → `rate == 1`, `converted_amount == amount`.
3. **Unsupported currency** — `USD→XYZ` → `400` with structured detail.
4. **Invalid amount** — `amount <= 0` → `422`.
5. **Bad code format** — `us`, `usdd`, digits → `422`.
6. **Service unit tests** — cross-rate math and rounding independent of HTTP.

## 7. Real-Integration Options (for a follow-up ticket)

The contract above is provider-agnostic. Proposed options to replace the mock,
ordered by recommendation:

1. **Frankfurter API** (frankfurter.app) — free, no API key, ECB-sourced daily
   rates. Lowest-friction for a first real integration; good for non-realtime
   use. Limitation: daily granularity, limited currency set.
2. **European Central Bank (ECB) reference rates** — fetch/parse the ECB XML
   feed, cache daily. Free, authoritative, no key; EUR-based cross rates.
3. **Open Exchange Rates / Fixer.io / exchangerate.host** — commercial APIs with
   API keys, higher rate limits, more currencies, historical + intraday data.
   Requires secret management (env var, never committed).
4. **Internal treasury/pricing service** — if the org has one, integrate via its
   internal API for authoritative, business-approved rates.

Recommended integration design (keeps the public contract stable):
- Introduce a `RateProvider` protocol/interface with `get_rate(from, to) ->
  (Decimal, as_of)`.
- Implement `MockRateProvider` (this ticket) and, later,
  `HttpRateProvider` adapters per source.
- Inject the provider into `CurrencyExchangeService` via `dependencies.py`, so
  swapping providers is a one-line DI change plus config.
- Add a **caching layer** (TTL cache) in front of live providers to reduce calls
  and cost.
- Manage provider credentials via environment variables / secrets — never in
  source. Add resiliency (timeouts, retries, circuit breaker) and a fallback to
  the mock/last-known rate.
- Consider persisting an audit trail of conversions (new table + repository)
  once real rates are used.

## 8. Non-Functional / Future Considerations
- **Precision:** standardize on `Decimal` end-to-end; define rounding policy
  (2 dp, `ROUND_HALF_EVEN`) centrally.
- **Auth & rate limiting:** none today; add before exposing publicly.
- **Observability:** structured logging of provider, rate, latency.
- **Idempotency:** optional `Idempotency-Key` header once side-effects exist.
